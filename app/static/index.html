    GraphRAG 입문

    RAG는 "질문과 비슷한 문장"을 찾아 줍니다. 하지만 답이 여러 장(章)에 흩어져 있고, 그 부분들이 관계로만 이어져 있다면 어떻게 될까요? 오늘은 교재 자료인 한국은행 보고서 「혁신과 경제성장 – 우리나라 기업의 혁신활동 분석 및 평가」(2024.5, 49쪽)로 벡터 RAG와 GraphRAG를 직접 비교합니다.

    벡터 RAG · 오늘의 실험 결과

    "저업력 중소기업이 겪는 자금 측면의 어려움은 무엇이고, 그 배경으로 지목된 자금 공급 주체의 우리나라 접근성 순위는?"

    자금조달 어려움을 다룬 2장 문서(doc09)는 찾지만, 벤처캐피탈 접근성 OECD 24위가 적힌 3장 문서(doc11)는 놓칩니다. 대신 "우리나라 기업 R&D가 OECD 2위"라는 다른 순위 이야기(doc03)가 1등으로 올라옵니다. 필요한 사실 2개 중 1개 (k=3, 간이 임베딩).

    GraphRAG · 같은 질문
    저업력 중소기업겪음 →혁신자금조달 어려움← 기능 부족벤처캐피탈← 측정벤처캐피탈 접근성

    질문 속 두 엔티티 사이의 경로를 따라가 2장(문제)과 3장(원인)의 근거를 함께 찾습니다. 필요한 사실 2개 중 2개 (k=3).

    Part 1 · 기초

    그래프란 무엇인가

    그래프(Graph)는 노드(Node, 점)와 이를 잇는 엣지(Edge, 선)로 이루어진 자료구조입니다. 지하철 노선도, SNS 친구 관계, 웹 페이지 링크가 모두 그래프입니다. 핵심은 "무엇이 있나"가 아니라 "무엇이 무엇과 연결되어 있나"를 표현한다는 점입니다.

    직접 해 보기: 두 사람을 차례로 클릭하면 최단 경로를 찾습니다
    출발 노드를 클릭하세요노드 위에 마우스를 올리면 이웃(1-hop)이 강조됩니다.

    노드 · 엣지

    노드 = 개체(사람, 회사, 제품). 엣지 = 둘 사이의 관계. 노드에 연결된 엣지 수를 차수(degree)라고 합니다.

    방향 · 라벨

    "기초연구 → 특허피인용건수"처럼 방향이 있고, 엣지에 IMPROVES 같은 이름(라벨)이 붙으면 의미를 표현할 수 있습니다.

    경로 · hop

    엣지를 따라 이동하는 길이 경로입니다. 한 번 이동이 1-hop입니다. 멀티홉 추론 = 그래프 경로 탐색입니다.

    지식그래프(Knowledge Graph)

    트리플 (RDF 방식)

    모든 지식을 (주어, 관계, 목적어) 세 개짜리 사실로 표현합니다.

    (기초연구, IMPROVES, 특허피인용건수)
(대기업, SUFFERS, 혁신실적의 질 정체)
(투자회수시장, ENABLES, 벤처캐피탈 접근성)

    속성 그래프 (Property Graph)

    노드와 엣지가 속성(key-value)을 가질 수 있습니다. Neo4j 같은 그래프 DB와 대부분의 GraphRAG 도구가 이 방식입니다.

    (:Policy {name:"산학 연구협력 강화"})
  -[:RAISES {성장률:"+0.18%p", 출처:"doc16"}]->
(:Outcome {name:"경제성장률"})

    지식그래프에 허용되는 노드·관계 타입의 목록을 미리 정한 것을 스키마 또는 온톨로지라고 합니다. 스키마가 있으면 추출이 일관되고, 없으면 유연하지만 지저분해집니다. 이 차이는 뒤에서 GraphRAG의 핵심 쟁점으로 다시 나옵니다.

    실습 코드: — networkx로 이웃, 최단 경로, PageRank, 커뮤니티를 계산합니다.

    Part 2 · 개념

    왜 GraphRAG가 생겨났나

    보고서는 문제(2장) → 원인(3장 앞부분) → 실증(3장) → 정책 효과(4장) → 처방(5장) 순서로 쓰여 있습니다. "중소기업 자금 문제"에 관한 사실만 해도 여러 장에 흩어져 있습니다.

    doc09 · 2장저업력 중소기업, 외부자금 부족 응답 9.9% → 45.4%
    →
    doc10 · 3장원인: 벤처캐피탈의 혁신자금 공급기능 부족
    →
    doc11 · 3장벤처캐피탈 접근성 OECD 24위, 정부 VC 주도
    →
    doc13 · 3장투자회수시장(M&A·IPO)이 발달해야 효과
    →
    doc18 · 5장처방: M&A 시장 활성화, 독립·기업 VC 역할 확대

    청크 입장에서 보면

    doc11의 "24위" 청크에는 '저업력 중소기업'이라는 말이 없습니다. 질문과 표현이 겹치지 않으니 벡터 검색은 이 청크를 뒤로 밀고, 대신 "우리나라", "OECD", "순위(2위)" 같은 표현이 겹치는 엉뚱한 청크(기업 R&D 순위, doc03)를 올립니다.

    그래프 입장에서 보면

    각 문서가 남긴 관계(겪음, 기능 부족, 측정, 가능하게 함)를 이으면 저업력 중소기업에서 벤처캐피탈 접근성까지 3-hop 경로가 됩니다. 경로 위 관계의 출처 문서가 바로 필요한 근거입니다.

    GraphRAG의 핵심 아이디어는 "문서를 미리 읽어 관계를 구조로 저장해 두고, 질문할 때는 구조를 따라 근거를 모은다"입니다. 비싼 이해(추출)를 인덱싱 시점에 미리 해 두는 대신, 질의 시점에는 연결을 빠르게 탐색합니다.

    질의: 그래프로 근거 모으기

    Local Search

    질문 속 엔티티를 찾고(Entity Linking), 그 주변 이웃과 연결 경로, 원문을 모읍니다. 특정 개체나 관계에 대한 질문에 씁니다.

    엔티티 연결→이웃·경로 확장→중요도(PPR) 순위→트리플 + 원문

    Global Search

    미리 만든 커뮤니티 요약 전체에 질문을 던져 부분 답을 얻고(Map), 점수가 높은 부분 답을 종합합니다(Reduce). "전체 주제·구조" 질문에 씁니다.

    요약 N개→ Map →부분 답 + 점수→ Reduce →최종 답

    DRIFT Search

    Global로 큰 방향을 잡은 뒤 후속 질문을 만들어 Local로 파고듭니다. Microsoft GraphRAG가 2024년 말에 추가한 하이브리드 방식입니다.

    Text2Cypher

    LLM이 자연어를 그래프 쿼리 언어(Cypher)로 번역해 DB에서 직접 실행합니다. 집계("몇 개?")와 정확한 필터에 강합니다.

    문서를 그래프로 바꾸는 방법과, LLM에게 맡겨도 되는가

    교재는 LangChain LLMGraphTransformer에 gpt-4o(temperature 0)를 붙여 문서를 그래프로 바꿉니다. 이 방법은 편리하지만, 기계가 만든 그래프를 그대로 믿어도 되는지는 따로 따져 봐야 합니다.

    문서 → 그래프 변환 방법들

    방법도구 예장점한계

    사람의 수작업도메인 전문가가 스프레드시트·온톨로지 도구로 작성가장 정확, 책임 소재 명확느리고 비쌈, 규모 확장 불가

    이 실습의 그래프는? data/kg.json(노드 45, 관계 60)은 LLM 자동 추출 결과가 아니라, 강의 자료를 만들 때 AI 어시스턴트가 보고서를 읽고 핵심 관계만 골라 수작업처럼 정리한 참조 그래프입니다. 핵심 수치는 원문과 대조했지만, 수업 전 강사 검수를 권장합니다. 실습 03()은 교재 방식(EXTRACTOR=lgt)과 직접 구현(custom)으로 LLM 추출을 실행한 뒤, 이 참조 그래프와 자동으로 비교합니다.

    LLM으로 그래프를 기계식 생성하는 것의 적절성: 여섯 가지 관점

    ① 정확성: 지어낸 관계와 빠진 관계

    LLM은 문서에 없는 관계를 그럴듯하게 만들기도 하고(환각), 여러 문장에 걸친 관계나 표·각주 속 수치는 자주 놓칩니다. 그래프에 들어간 오류는 이후 검색·답변까지 그대로 전파되며, 검색 단계에서는 오류인지 알 수 없습니다.

    ② 재현성: temperature 0은 '같은 결과'를 보장하지 않는다

    temperature 0은 무작위성을 줄일 뿐, 서버의 병렬 계산 방식이나 모델 버전 교체 때문에 결과가 달라질 수 있습니다. 게다가 최신 추론 모델은 temperature 자체를 받지 않는 경우가 많습니다. 재현성은 구조화 출력(JSON 스키마) + 결과 스냅샷 저장 + 모델 버전 고정으로 확보하는 편이 현실적입니다.

    ③ 의미 손실: 경제 보고서의 '유보'와 '조건'이 사라진다

    보고서는 "~일 가능성이 있다", "투자회수시장이 발전한 경우에만 유의", "모형 추정치" 같은 표현으로 주장의 강도를 조절합니다. (벤처캐피탈, CAUSES, 자금조달 어려움) 같은 트리플은 이 뉘앙스를 지우고 추정·상관을 확정된 인과처럼 보이게 합니다. 관계에 확신도·조건·근거 문장을 속성으로 남겨야 합니다.

    ④ 일관성: 관계 이름과 개체 이름이 흔들린다

    자유 추출에서는 같은 관계가 CAUSES·LEADS_TO·RESULTS_IN으로, 같은 개체가 "벤처캐피탈·VC·벤처투자"로 나뉩니다. 그래프가 조각나면 경로 탐색이 끊깁니다. 스키마 기반 추출과 엔티티 해소가 필수인 이유입니다.

    ⑤ 검증 가능성과 책임

    정책 판단이나 강의 자료처럼 틀리면 곤란한 곳에 쓴다면, 모든 관계에 출처 문서·문장을 달아 사람이 되짚을 수 있어야 합니다. 전수 검수가 어렵다면 무작위 표본을 뽑아 검수하고 정밀도를 보고합니다. 외부 API로 문서를 보내는 것이 허용되는지(저작권·보안)도 함께 확인해야 합니다.

    ⑥ 비용과 규모

    49쪽 보고서는 청크 100여 개라 부담이 없지만, 문서가 수만 건이면 추출 비용과 시간이 벡터 인덱싱의 수십 배가 됩니다. LazyGraphRAG·LightRAG가 나온 배경입니다. 반대로 작은 핵심 문서에는 사람이 스키마를 잡고 LLM이 초안을 만든 뒤 사람이 검수하는 방식이 가장 효율적입니다.

    관찰 ① 많이 뽑지만 핵심을 놓친다

    LLM은 참조보다 5~8배 많은 관계를 만들었지만, "저업력 중소기업이 혁신자금조달 어려움을 겪는다" 같은 핵심 관계는 놓치거나 "중소기업(업력 하위 20%)"처럼 다른 이름으로 만들었습니다. 관계 이름도 106~158종으로 흩어졌습니다.

    관찰 ② temperature 0인데도 매번 다르다

    관찰 ③ 문서 메타 정보가 섞인다

    "경제전망보고서 → CONTAINS → 한국기업혁신조사"처럼 내용이 아닌 출처·방법론 관계가 다수 생겼습니다. 스키마와 프롬프트로 "무엇을 뽑을지"를 정해야 하는 이유입니다.

    Part 2 · 개념

    벡터 RAG vs GraphRAG: 무엇이 다른가

    둘은 경쟁 관계라기보다 검색의 기준이 다릅니다. 벡터 RAG는 "의미가 비슷한가", GraphRAG는 "구조적으로 연결되어 있는가"를 봅니다.

    관점벡터 RAGGraphRAG
    저장 단위청크(텍스트 조각) + 임베딩 벡터엔티티·관계(트리플) + 원문 링크 + (커뮤니티 요약)
    인덱싱 과정분할 → 임베딩분할 → LLM 추출 → 엔티티 해소 → 그래프 구축 → (커뮤니티 탐지 → 요약) → 임베딩
    인덱싱 비용임베딩 호출만 (저렴하고 빠름)청크마다 LLM 호출. 원조 MS GraphRAG는 벡터 RAG보다 훨씬 비쌈 → LazyGraphRAG, LightRAG가 이를 줄이려 등장
    검색 기준의미적 유사도 (코사인)구조적 연결성: 이웃, 경로, 중심성, 커뮤니티
    검색 연산Top-k 최근접 이웃 탐색엔티티 연결 → k-hop 확장 / 최단 경로 / Personalized PageRank / 요약 Map-Reduce / Cypher
    LLM에 주는 컨텍스트원문 청크 나열관계 트리플·경로·커뮤니티 요약 + 원문
    강한 질문답이 한 곳에 있는 사실 질문, 표현이 다양한 질문멀티홉, 관계, 인과 연쇄, 전역 요약, 집계
    약한 질문멀티홉, 전역 요약, 집계추출 단계에서 빠진 정보, 관계로 표현하기 어려운 뉘앙스, 단순 질문(과잉 설계)
    설명 가능성"이 청크가 질문과 비슷해서""A → B → C 경로 때문에" (근거 경로를 보여 줄 수 있음)
    데이터 갱신새 청크를 추가하면 끝엔티티 병합, 커뮤니티 재계산이 필요. LightRAG, Graphiti는 증분 갱신 지원
    실패 양상관련 문서 누락, 비슷하지만 틀린 청크추출 오류, 중복 엔티티, 지어낸 관계가 검색까지 그대로 전파
    인프라벡터 DB (Chroma, FAISS, pgvector 등)그래프 저장소(networkx, Neo4j 등) + 대개 벡터 인덱스도 함께
    평가검색 Recall, 답변 정확도+ 그래프 품질(추출 정밀도·재현율, 엔티티 중복률)
    LangChain 구성요소TextSplitter · Embeddings · VectorStore · Retriever · LCEL+ with_structured_output(추출) · networkx/Neo4jGraph · GraphCypherQAChain · create_agent(도구 탐색)

    흔한 오해: "GraphRAG가 벡터 RAG보다 항상 낫다"는 사실이 아닙니다. 여러 벤치마크 연구에서 단순 사실 질문은 벡터 RAG가 비슷하거나 더 나았고, 그래프의 이점은 멀티홉·전역 질문에 집중되었습니다. 실무 표준은 둘을 섞는 하이브리드입니다. 아래 실험에서 직접 확인해 봅시다.

    지식그래프 + 언어모델 연구

    한계 KG를 사람이 만들어야 해서 비싸고, 사내 문서 같은 비정형 텍스트와 동떨어짐
    2020

    RAG 등장 (Lewis 외, Facebook AI)

    LLM이 외부 문서를 검색해 답하게 한 프레임워크. 지금 수업에서 배우는 벡터 RAG의 원형입니다.

    남은 과제 청크 단위 유사도 검색이라 멀티홉과 전역 질문에 약함
    2023

    Think-on-Graph (ToG)

    LLM이 에이전트처럼 KG 위를 빔서치로 탐색하며 다음에 따라갈 관계를 스스로 고릅니다.

    기여 "관계를 이해하며 탐색"한계 잘 만들어진 KG가 있어야 함, LLM 호출 많음
    2024.01

    RAPTOR

    청크를 재귀적으로 클러스터링·요약해 트리를 만듭니다. 그래프는 아니지만 "계층 요약으로 전역 질문에 답한다"는 아이디어를 보여 줬습니다.

    2024.02

    G-Retriever · GNN 계열

    그래프 신경망(GNN)으로 관련 서브그래프를 골라 LLM에 전달합니다. 뒤이어 GNN-RAG(2024.05) 등이 나왔습니다.

    한계 학습 데이터·모델 훈련이 필요해 실무 도입이 어려움
    2024.04 → 07

    Microsoft GraphRAG ("From Local to Global")

    LLM이 문서에서 KG를 자동으로 만들고, Leiden 커뮤니티마다 요약을 미리 생성해 Global Search로 전역 질문에 답합니다. 7월 오픈소스 공개 후 "GraphRAG" 붐이 시작됐습니다.

    해결 KG 구축 비용(사람) 문제, 전역 질문남은 과제 인덱싱 LLM 비용이 매우 큼, 문서 추가 시 재계산
    2024.05

    HippoRAG

    뇌의 해마 기억 이론에서 착안. 추출한 KG에 Personalized PageRank를 돌려 한 번의 검색으로 멀티홉 근거를 찾습니다. 오늘 실습 04의 순위 계산이 이 아이디어입니다.

    2024.09

    KAG (Ant Group)

    스키마·논리 형식 기반의 지식 증강 생성. 금융·의료처럼 정확성이 중요한 전문 도메인을 겨냥했습니다.

    2024.10

    LightRAG · DRIFT Search

    LightRAG는 커뮤니티 요약 없이 엔티티(저수준)와 주제 키워드(고수준) 이중 검색을 하고 증분 업데이트를 지원해 가볍습니다. 같은 시기 MS는 Global과 Local을 잇는 DRIFT Search를 공개했습니다.

    해결 비용, 업데이트
    2024.11

    LazyGraphRAG (Microsoft)

    요약을 미리 만들지 않고 질의 시점까지 LLM 처리를 미룹니다. 인덱싱 비용을 벡터 RAG 수준으로 낮추는 것이 목표입니다.

    2025.01

    Zep · Graphiti — 시간 인식 지식그래프

    관계마다 유효 기간을 두고, 모순되는 새 사실이 오면 옛 사실을 무효화합니다. GraphRAG가 에이전트의 장기 기억으로 확장된 사례입니다.

    2025

    HippoRAG 2 · PathRAG · NodeRAG · HyperGraphRAG

    경로 단위 가지치기(PathRAG), 이질적 노드 설계(NodeRAG), 셋 이상을 잇는 하이퍼엣지(HyperGraphRAG) 등 검색 품질과 표현력을 다듬는 연구가 이어졌습니다.

    2025

    평가와 회의론: GraphRAG-Bench 등

    "언제 그래프가 실제로 이기는가"를 체계적으로 측정하기 시작했습니다. 이점은 멀티홉·전역 질문에 집중되고 단순 질문에서는 이점이 작다는 결과가 반복됐습니다.

    2025 → 2026

    Agentic · 하이브리드 · 스키마

    고정 파이프라인 대신 LLM 에이전트가 그래프 도구(MCP 서버 등)를 골라 쓰고, 벡터+키워드+그래프 하이브리드가 표준이 되었습니다. 엔터프라이즈에서는 스키마를 먼저 정하는 추출로 돌아가는 흐름이 강해졌습니다. MS GraphRAG는 3.x까지 판을 올렸습니다.

    Part 5 · 현재

    최신 트렌드와 남은 과제 (2025–2026)

    비용 절감: Lazy · Lite

    질의 시점까지 처리를 미루거나(LazyGraphRAG), 요약을 생략하거나(LightRAG), 추출 전용 소형 모델을 씁니다. 증분 인덱싱도 기본이 되었습니다.

    Agentic GraphRAG

    에이전트가 search_entity, get_neighbors, find_path, run_cypher 같은 도구를 골라 반복 호출합니다. 그래프 DB를 MCP 서버로 노출하는 패턴이 확산되었습니다.

    에이전트 메모리 = 시간 인식 KG

    Graphiti/Zep, Mem0, Cognee 등이 대화에서 사실을 뽑아 그래프로 쌓고, 유효 기간으로 모순을 처리합니다.

    하이브리드가 표준

    벡터(의미) + BM25(키워드) + 그래프 확장(관계) → 리랭커. 그래프 DB가 벡터 인덱스를 내장하는 것도 일반적입니다.

    스키마·온톨로지의 귀환

    자유 추출은 노이즈가 많아 엔터프라이즈에서는 도메인 스키마를 먼저 정하고 그 안에서만 추출합니다.

    표현력 확장

    n-ary 관계(하이퍼그래프), 표·이미지 노드(멀티모달), 코드 저장소의 호출 그래프(코딩 에이전트 컨텍스트)로 넓어지고 있습니다.

    남은 과제

    과제내용관련 실습
    추출 품질LLM이 관계를 빠뜨리거나 지어냄. 오류가 검색까지 전파됨
    엔티티 해소같은 개체의 다른 표기를 병합하는 문제. 가장 과소평가된 단계
    비용·지연인덱싱 LLM 호출 비용, Global Search의 Map-Reduce 지연
    갱신과 일관성문서가 바뀌면 그래프와 요약을 어떻게 갱신하나, 모순된 사실은?
    평가그래프 품질과 최종 답변 품질을 함께 재는 표준 벤치마크가 아직 부족
    롱컨텍스트와의 경쟁컨텍스트 창이 커져 "다 넣으면 되지 않나"는 반론. 대규모 코퍼스에서는 비용과 지연 때문에 구조화가 여전히 유리하다는 쪽이 우세토론
    보안Text2Cypher는 LLM이 만든 쿼리를 DB에서 실행함. 읽기 전용 계정, 쿼리 검증 필요

    Part 5 · 현재

    최근 많이 쓰는 GraphRAG 환경과 초기 셋팅

    도구형태강점이럴 때
    Microsoft GraphRAGCLI 파이프라인 (graphrag 3.x)커뮤니티 요약, Local·Global·DRIFT·basic 검색, 프롬프트 자동 튜닝전역 요약 질문이 중요, 비용 여유
    LightRAG파이썬 라이브러리 + 서버/웹 UI가볍고 빠름, 증분 삽입, 5가지 검색 모드빠르게 프로토타입, 문서가 자주 추가됨
    Neo4j + LangChain그래프 DB + langchain-neo4jCypher, 벡터 인덱스 내장, 운영 도구, 시각화서비스 운영, 정형 스키마, 집계 질의
    Graphiti (Zep)파이썬 라이브러리 (+Neo4j 등)시간 인식 KG, 에피소드 단위 증분 갱신에이전트 장기 기억, 사실이 계속 바뀜
    직접 구현 (이 실습)LangChain + networkx원리 이해, 의존성 최소수업, 소규모 실험

    아래 명령과 코드는 2026년 9월 기준 최신 패키지(graphrag 3.2, lightrag-hku 1.5, graphiti-core 0.30, langchain 1.4)로 API를 확인했습니다. 버전이 바뀌면 옵션이 달라질 수 있습니다.

    Part 6 · 실습

    실습 로드맵

    카드를 누르면 코드가 열립니다. 라이브 실험실은 python app/server.py로 띄운 서버가 이 코드를 그대로 import 해서 실행합니다. 키 없이 실행은 API 키 없이 돌아가고, LLM 필요는 .env의 LLM_MODEL이 있어야 전체 기능이 동작합니다(없으면 검색 결과만 보여 줍니다).

    언제 GraphRAG를 써야 할까

    상황추천
    단순 FAQ, 사실 검색벡터 RAG + 리랭커로 충분
    멀티홉·인과 연쇄 질문이 잦음그래프 경로·PPR 확장 + 벡터 하이브리드 (HippoRAG 2, LightRAG)
    "전체 요약/테마" 질문커뮤니티 요약 기반 Global Search (MS GraphRAG, LazyGraphRAG)
    도메인 스키마가 명확함 (금융, 제조)스키마 기반 KG + Neo4j + Text2Cypher
    문서·사실이 계속 바뀜증분 갱신 도구 (LightRAG, Graphiti)
    에이전트 장기 기억시간 인식 KG (Graphiti/Zep, Mem0)

    오늘의 요점

    • 그래프 = 노드와 엣지. 멀티홉 추론 = 경로 탐색
    • GraphRAG는 인덱싱 때 관계를 추출해 두고, 질의 때 구조를 따라 근거를 모은다
    • 강점은 멀티홉·전역 질문, 약점은 추출 비용과 품질
    • 실무는 하이브리드, 그리고 에이전트·메모리로 확장 중
